# Design review — Round 02 (2026-09-05)

6 facets · 23 proposals · 23 survived critique · 776620 tokens · 13 agents

Facets: orchestrator-auth-identity, eval-and-prompt-governance, cloud-legal-basis, capacity-model-and-latency, data-lifecycle-dpia, client-ux-and-continuity

## Highest-leverage change

Unpublish the data-plane ports and put a single identity-terminating proxy in front of the orchestrator (orchestrator-auth-identity P1, bundled with the no-identity lane P3). The immediate sub-step - deleting the host port mappings for langgraph, litellm, ollama and postgres from docker-compose.yml - is a four-line edit that closes the widest hole today: :4000 exposes the LiteLLM master key, :11434 is raw unauthenticated Ollama, :5432 is Postgres, and :8888 is an auth-free FastAPI that will call the Anthropic cloud. The proxy itself is one well-understood container and one Entra app registration, with no change to main.py's routing logic beyond a ~30-line JWT-check dependency. Value is disproportionate: Round 1 explicitly identified 'no auth on :8888' as the precondition blocking all ACL, per-agent quota, RAG-ACL and cache-namespace work, so this single change unblocks roughly half the remaining roadmap. Risk is low provided it ships with the bounded no-identity lane so a satellite/Entra outage degrades to local T1-T2 service instead of a total outage. Runner-up on value/effort is the prompt-pack extraction, which lands immediately with zero dependencies and fixes the fact that the 'legal model' currently runs with no system prompt at all.

## Top proposals to adopt (ranked, post-critique)

### 1. Identity-terminating proxy + unpublish the data-plane ports + bounded no-identity lane
_facet: orchestrator-auth-identity_

**Why:** Round 1 named 'no auth on :8888' as the blocker for every ACL, quota, RAG-ACL and cache-namespace item, and the code confirms it: FastAPI has zero auth middleware and docker-compose.yml publishes :8888, :4000 (LITELLM_MASTER_KEY), :11434 (raw Ollama), :5432 (Postgres) and :3000 (Grafana) straight onto the Docker host. Anything on the host or any sibling container reaches the orchestrator and the model backends unauthenticated. Given M365 F3 (no Entra App Proxy, no Conditional Access, no P1), a self-hosted oauth2-proxy running the Entra OIDC auth-code flow and injecting a proxy-signed JWT (oid, UPN, group/role claims, tenant) is the minimum viable fix. It must ship bundled with a bounded no-identity lane so that a satellite/identity-plane outage - a normal multi-island condition - degrades to local T1-T2 Q&A instead of a total outage, otherwise login.microsoftonline.com becomes a single point of failure for an on-prem system whose whole point is local resilience. This is foundational: it turns identity into a verified input struct the router, cache key, RAG ACL and T5 ledger all read from one place.

**Sketch:** Add one oauth2-proxy container on the sovereign-ai bridge net as the only host-published entrypoint for the human-facing orchestrator/UI. Remove the host port mappings for langgraph, litellm, ollama, postgres from docker-compose.yml (they need no public ingress); Grafana keeps a port but switches to its own Entra OIDC. One Entra app registration; use app roles / app-assigned security groups surfaced as role claims to dodge the group-overage cap. In main.py add a ~30-line dependency that rejects any request without a valid proxy-signed JWT and builds a RequestContext dataclass {subject_oid, roles, tenant, created_at, purpose-enum} threaded into route_t5 and future cache/RAG calls. Define a client-credentials token path for service-to-service and future RAG /ingest. The no-identity lane enters through the same proxy in a configured unauth-passthrough mode that stamps identity:none, clamps start tier to T2 before any fallback, blocks RAG, cache writes and T5 structurally, and is rate-limited by one global token bucket (not per-source-IP, which is broken behind a proxy). Add degradation_reason=identity_unavailable to the Round 1 typed contract and an identity_unavailable_ratio gauge with an alert on sustained non-zero. Work: M - one container, compose edits, ~1 day of orchestrator middleware, plus Entra registration plumbing and a leak-canary test proving the anonymous lane cannot reach T5/RAG/cache-write.

### 2. Curated canonical answer base for the recurring core
_facet: capacity-model-and-latency_

**Why:** This is the single largest capacity multiplier and the thing that makes CPU-only viable for 5500 real agents rather than a pilot. Helpdesk load is dominated by a few hundred questions (reinit mot de passe, VPN satellite, MFA, licences M365 F3, conges, materiel); serving that 50-60% fraction from a vetted, human-reviewed answer store at ~10ms with zero inference removes it from the cascade entirely and makes 'reponse differee' the visible minority instead of the default experience. Human-reviewed canonical answers are also safer for RGPD and quality than freshly generated (and freshly hallucinated) ones, and the base keeps answering when inference is fully down. The blast radius inverts, though: a wrong or stale canonical answer is served instantly and authoritatively to thousands, so it needs guardrails before go-live.

**Sketch:** Sequence after the pgvector/embeddings RAG layer (planned, not built - the free-text-to-canonical match needs it). Mine the query log for the top ~30-50 clusters first (not 300), measure the real hit rate, then expand. Offline nightly pipeline drafts one canonical French answer per cluster; a named editorial owner validates in batches (T4 or the deliberate T5 path is RGPD-safe here because the content is generic, non-nominative). Store validated answers in the cache/RAG layer keyed by cluster. Mandatory guardrails: semantic match must fail toward the live cascade below a conservative confidence threshold; per-answer 'review-by' date surfaced to the owner; one-click unpublish; a 'ce n'est pas ma question / reponse obsolete' feedback button that re-queues with a flag. Register query-log mining as a processing purpose. Work: M for the pipeline + first 30-50 answers; recurring ~0.3 FTE editorial - must be a funded, named staffing ask or the base rots.

### 3. DPIA-as-code: one manifest, a nightly reaper, LiteLLM metadata-only logging
_facet: data-lifecycle-dpia_

**Why:** This is the connective tissue the legal, cache, queue and RAG work all need, and it matches the CLAUDE.md eval-harness-first ethos: retention becomes a falsifiable, tested property instead of 'Postgres volumes grow forever, nobody knows what is in them'. One checked-in YAML enumerating every store that can hold nominative or pseudonymised data (LiteLLM logs, checkpointer state, job queue, response cache + embeddings, egress ledger, eval corpus, pseudonymisation register, RAG chunks) with lawful basis, purpose, categories, location, reversible y/n, TTL and erasure procedure is simultaneously the CNIL Article 30 register, the reaper's config source, and the gate that a new store cannot be added without appearing in it. The observation that LiteLLM should run metadata-only (turn_off_message_logging, no body persistence) removes an entire pseudonymised-PII store for near-zero effort and directly constrains the T5-through-LiteLLM refactor so it does not reintroduce body logging.

**Sketch:** Create api/legal/data_manifest.yaml with one entry per store. Add a nightly reaper container (or cron in an existing one) that enforces every TTL column, emits rows_purged_total{store}, and alerts if any store missed a purge in 25h. Set native TTL where possible: checkpointer/queue threads expire at 24-48h (record 'no multi-day conversation memory' as an accepted product decision in the manifest), Prometheus tsdb.retention, LiteLLM config metadata-only. Add a CI check mapping every Postgres table and named volume to a manifest entry. Make the erasure drill (seed a canary subject across all stores, fire the erasure primitive, assert zero residual) a scripted docker compose target run pre-release or monthly, not per-commit. Work: M - the manifest is a day, the reaper a day, the CI check an hour, LiteLLM config a one-liner.

### 4. Extract every behaviour-defining prompt into a versioned, fingerprinted prompt pack
_facet: eval-and-prompt-governance_

**Why:** Code-confirmed: query_ollama sends the user prompt raw with no system field, so T1-T4 answer with zero French enforcement, no 'reponse indicative, non juridique' framing, no Article-9 refusal and no defence against 'ignore les consignes / reponds en anglais'. The only system prompt in the stack is the inline three-line T5 string in main.py. 'The legal model' is literally 'whatever dolphin-mixtral does raw'. Turning that into a diffable, fingerprinted artifact is the precondition for ever detecting that a later change moved it, and it is the highest-leverage item in this facet because it lands NOW with no dependency on the Round 1 corpus - extraction plus fingerprint plus manual PR review deliver value pre-harness. It strictly improves the local path with no RGPD or sovereignty cost. It must also account for the broken-fallback interaction: query_ollama_with_fallback walks a failed T5/T4 legal query down to T1, so the T1 prompt is silently a legal-disclaimer surface.

**Sketch:** Create a single config/prompts.yaml with per-tier keys (version, owner, body) - not one file per tier with semver ceremony. Load at startup with fail-fast; CI schema-validates the pack so a typo never reaches deploy. main.py stamps a prompt-set fingerprint (hash of all loaded prompts) into the /query response and one low-cardinality Prometheus label - not every log line. Give T1 and T2 disclaimer-bearing prompts because they are the T5/T4-failure fallback sink; give T4 explicit 'reponse indicative non juridique' + Article-9 refusal framing. One GOVERNANCE.md owns the prompt index alongside the cascade table, the category->tier map and the Anone PII label set, under one named owner. Wire the eval-diff sign-off gate only once the harness exists. Work: S-M - extraction and wiring is 1-2 days; the ongoing cost is the review cadence.

### 5. cloud_authorization.yaml + api/legal/ artifacts + fail-closed startup gate
_facet: cloud-legal-basis_

**Why:** Right now route_t5_with_anonymization calls anthropic.Anthropic().messages.create() with no recorded transfer basis, and .env just flips ANTHROPIC_API_KEY between a real key and 'disabled'. There is literally no documented lawful basis for the cloud transfer and no mechanism preventing code drifting away from whatever the DPIA eventually says. A machine-readable cloud_authorization.yaml {t5_enabled, legal_basis: SCC+TIA|none, dpia_ref, tia_ref, singling_out_gate_required, signed_by, signed_date, review_due, review_owner} that main.py reads at startup - hard-failing the T5 path closed to local and reporting it on /health if legal_basis is 'none' or review_due has passed - converts the facet's core question from a debate into a signed, versioned, expiring file a regulator can be handed. It fits a small team: one YAML, one startup check, one cron reminder. It must be paired with the Round 1 decision that cloud is escalation-only and the cascade is capped at T4, and it enforces presence and expiry only, never validity - an annual DPO/external review is the real control.

**Sketch:** Create api/legal/ with dpia.md, tia.md (the FISA 702 / EO 12333 analysis; supplementary measures = singling-out gate + zero-retention terms + escalation-only), ropa.yaml (Article 6 basis per tier - public task 6(1)(e) for the helpdesk, Article 9 terms on-prem-only), and cloud_authorization.yaml. Ship only Regime B (SCCs + TIA for a pseudonymised transfer) as operative; keep any 'effectivement anonyme / out of Chapter V' claim documented but disabled pending a standalone signed legal opinion, because main.py retains the pii_mapping key at deanonymisation time so the transfer stays in scope. Eval metrics (cloud-call-rate, PII-canary counts) go to a separate machine-written api/legal/metrics.json the human docs cite by reference - signed docs stay immutable between reviews. Access-control or flag api/legal/ as sensitive. Also route the T5 call through LiteLLM (:4000) so the Anthropic key lives in one container and all cloud traffic hits one spend/audit log - with LiteLLM message logging OFF. Work: M engineering (startup gate, egress-decision function, LiteLLM refactor) + the real cost is the DPO/legal deliverable.

### 6. Honest two-lane capacity model: immediate vs deferred, concurrency=1, one projected-wait gauge
_facet: capacity-model-and-latency_

**Why:** The current httpx timeout is 120s and T3/T4 answers on the CPU-only box routinely blow it; there is no queue, no cache, no deferred path. Splitting the service into a bounded synchronous product (cache/RAG hits + a hard-capped ~40-token T1 reformulation) and an asynchronous 'reponse differee' product (all T2-T5 work, answered by notification) gives the queue a real meaning and sets political expectations honestly up front. Paired with OLLAMA_NUM_PARALLEL=1 (currently defaulted to 2 - on CPU two concurrent generations just make both miss their deadline) and a serialized request queue, per-request latency becomes deterministic (wait = queue_depth x mean_answer_time) and collapses to one Grafana gauge ops and management can both read. Reject the EWMA closed-loop governor from the same proposal - it is a stateful control loop a 2-3 person team cannot debug at 2am and CLAUDE.md guideline 2 pushes back hard; a static admission rule with one knob does the job until the RTX 3090 lands and real load data exists.

**Sketch:** Set OLLAMA_NUM_PARALLEL=1 and add a serialized queue in the orchestrator (or Postgres-backed for the deferred lane, anonymised text only for the T5 subset, raw-encrypted-sovereign + 24-48h TTL for local jobs, listed in the DPIA manifest). Router decision becomes binary: if estimated_tokens / measured_static_tok_s > deadline_s, refuse synchronously and enqueue. One tunable knob (deadline_s), one Grafana gauge ('attente projetee pour une nouvelle requete T3'), one alert on sustained shed-rate. Raise the 120s httpx timeout. Publish the SLA as 'heures ouvrees, best effort' with NO number until drain capacity is measured. Semantic-similarity dedupe on re-asks with a 'votre question est deja en file, reponse estimee HH:MM' response. Work: M - concurrency flag is one line, the queue and admission rule are the bulk, notification plumbing depends on the client decision.

## Contradictions (and resolutions)

- CACHE KEY vs IDENTITY (orchestrator-auth P2 RequestContext vs Round 1 response cache P5 and canonical answer base): hashing the caller's Entra group set into the cache key drives cross-user hit rate toward zero across 5500 agents (nearly every user has a unique group set), defeating the cache the key was meant to protect. Resolution: cache key = sha256(sensitivity_tier || normalized_query) with 3-4 coarse data-sensitivity tiers (public / interne / RH-restreint), NOT caller identity. Persist a full identity snapshot only on the T5 egress ledger; for cache and RAG store a sensitivity label and re-check live Entra claims at read time.
- SSO AS HARD DEPENDENCY vs MULTI-ISLAND RESILIENCE (orchestrator-auth P1 vs P3 and brief constraints a/e): an internal-only orchestrator that rejects anything not proxy-signed makes login.microsoftonline.com reachability a whole-stack dependency for a system whose purpose is local satellite resilience. Resolution: adopt P1 and P3 as one bundle, never P1 alone. The no-identity lane enters through the same proxy in unauth-passthrough mode (never a second open port), is clamped to T2, and cannot reach T5/RAG/cache-write. Long proxy session cookie lifetime so only new logins and post-expiry users hit the lane during an outage.
- TEAMS BOT TRANSPORT vs SOVEREIGNTY AND eDISCOVERY (client-ux P1 vs cloud-legal facet and data-lifecycle P4 split-logging): routing 100% of queries through Azure Bot Service in clear, before Anone, contradicts the stated bar ('nothing nominative in clear to any cloud') and puts every query into M365 Purview/eDiscovery scope where a tenant admin can retrieve an agent's sensitive question by name. Resolution: primary client = Entra-authenticated PWA served from the box with an async queue and web-push/email notification, so query content never leaves the sovereign perimeter. Use Teams ONLY for the approver-side T5 moderation gate, where the payload is the already-anonymised query or just metadata.
- EWMA CAPACITY GOVERNOR vs SIMPLICITY FIRST (capacity P2 vs CLAUDE.md guideline 2): a self-adjusting control loop with a documented 'mistuned threshold -> service feels dead' failure mode is exactly the magic a 2-3 person team cannot debug at 2am, and it needs cold-start seeding from an eval harness that does not exist. Resolution: adopt the trivial half unconditionally (OLLAMA_NUM_PARALLEL=1, serialized queue, one static projected-wait gauge, one deadline_s knob). Reject the per-model EWMA loop. Revisit a real control loop only after the RTX 3090 lands and load data exists.
- REGIME A 'EFFECTIVELY ANONYMOUS' vs KEY RETENTION (cloud-legal P1 vs data-lifecycle P1 and EDPB Jan-2025 pseudonymisation guidance): main.py keeps pii_mapping in-process and de-anonymises the answer, so the controller (DSI) retains the re-identification key; under EDPB guidance and CNIL practice the data stays personal for the sender and the transfer stays in GDPR Chapter V scope regardless of what Anthropic can do. A code switch labelled 'effectivement anonyme' encodes a legal bet a regulator is likely to reject and the log line becomes self-incriminating. Resolution: ship only Regime B (SCCs + TIA) as operative. Keep Regime A documented but disabled, requiring a standalone signed legal opinion that specifically addresses sender-side key retention, or a redesign where the map is dropped and the answer returned still-masked.
- CRYPTO-SHRED KEY SUBSYSTEM vs EPHEMERAL MAP LIFETIME (data-lifecycle P1 vs actual code): anone_api.py has no database - pii_mapping is returned in the HTTP response, used once by /deanonymize, then discarded; deanonymisation is synchronous and immediate. A persistent per-subject-key register with rotation/shred/backup-exclusion is a net-new store of reversible PII and a key-lifecycle subsystem a 2-person team will not sustain. Resolution: adopt the invariant 'every downstream store holds only tokenised text; exactly one store is reversible' as the DPIA backbone, but implement the reversible store as a short-TTL ephemeral register (seconds-to-minutes, disk-encrypted, never backed up). For single-subject Article 17, rely on the provenance/derivation fan-out (data-lifecycle P2 reframed as origin_request_id + source_doc_id columns and one idempotent erase() function), not key deletion.
- ANONE-AT-WRITE-TIME FOR EVERYTHING vs ANONE AS SPOF FOR LOCAL WORK (Round 1 cross-cutting finding vs data-lifecycle P1/P4, capacity P3): forcing GLiNER-at-0.5 on every T2-T4 queue job mangles text, risks de-anon failures, competes with Ollama for CPU on the fast path, and makes a 503-prone service block work that never leaves the building. Resolution: Anone runs at write time only for artifacts that can feed the T5 path or cross the perimeter (cross-user-servable cache entries, RAG chunks, eval corpus, the T5 queue subset). Local-only queue jobs store raw text encrypted at rest on sovereign storage with short TTL and no Anone.
- EVAL CORPUS AS CNIL METRIC vs PRODUCTION LEDGER (eval P2 reasoning vs cloud-legal P4): presenting a lab routing-accuracy number computed on synthetic/pseudonymised data as a CNIL transfer-compliance metric would mislead the operator. Resolution: the production egress ledger (Round 1 P3) counting actual cloud calls is the compliance metric; eval-corpus routing numbers are advisory quality signals only. State this explicitly in GOVERNANCE.md.

## Threads to go deeper (round 3)

- cloud-legal-basis: Given that main.py retains the pii_mapping key to de-anonymise the answer, is there ANY implementable architecture (return the answer still-masked and let the client re-map locally; drop the map entirely; a third party holds the key) under which a T5 call is NOT a GDPR Chapter V transfer - or is the honest engineering answer 'T5 is always an Article 46 transfer, budget the SCC+TIA deliverable and keep it escalation-only'? Name the exact legal deliverable, its author, and its cost.
- client-ux-and-continuity + orchestrator-auth-identity: Concrete design of the Entra-authenticated on-prem PWA - MSAL-in-browser vs oauth2-proxy for a SPA, the long-lived device-token path for PWA offline mode (which cannot do interactive OIDC), and exactly how the asynchronous 'votre reponse est prete' notification reaches an agent on a remote island WITHOUT transiting Microsoft (web-push over satellite, on-prem SMTP, polling).
- capacity-model-and-latency: What is the actually-measured throughput of the current CPU-only box - tok/s per model for prefill vs decode, serial vs 2-concurrent, cold vs warm - and what is the real query arrival rate and distribution? Define the measurement harness and run it BEFORE any SLA number, worker-pool size, or deadline_s value is committed. Without this every capacity number in these proposals is a guess.
- data-lifecycle-dpia: Store by store, decide which persisted artifacts MUST pass through Anone at write time versus may hold raw text encrypted on sovereign storage, and write the residual-identifier risk (GLiNER at 0.5 misses quasi-identifiers like 'la seule gestionnaire RH de Raivavae') into the DPIA entry for each. Resolve whether the operational query store is treated as anonymous, pseudonymised, or minimised-but-still-personal data.
- eval-and-prompt-governance + fix-fallback: Since query_ollama_with_fallback walks a failed T5/T4 legal query DOWN to T1 (weakest model answers the hardest question), should juridique/Article-9-category queries be structurally barred from downward fallback - failing to a typed 'deferred' or 'unavailable' response instead - and what exactly must the T1/T2 disclaimer prompts say given they are the current fallback sink?

## Facets / concerns missed

- Model supply chain and deployment provenance: how model weights are obtained, checksum-verified, pinned, updated and rolled back. The phantom 'Llama 3.3 8B' in CLAUDE.md vs the actual TIERS list (mistral:7b, llama2:7b, neural-chat, dolphin-mixtral) proves nobody owns 'which weights are actually running', and dolphin-mixtral / neural-chat are uncensored community fine-tunes being used as the legal and code tiers with no stated vetting.
- Production answer-quality observability (distinct from the offline eval harness): there is Prometheus/Grafana for latency and GPU but no facet on detecting a bad answer in the wild - user thumbs-down aggregation, sampled human review of live traffic, drift alerting, or a feedback loop from the 'ce n'est pas ma question' button back to routing and the prompt pack.
- Acceptable-use / content-safety / output filtering: 5500 agents, no auth today, and nothing governs an agent asking the system to draft something discriminatory, to process bulk citizen data for an improper purpose, or to generate disinformation. No AUP, no abuse rate-limiting distinct from fair-share quota, no output-side content check.
- RGPD Article 33/34 incident response: if the deanonymisation map leaks, or a cloud call sends PII in clear because GLiNER missed it, what is the detection-to-72-hour-notification runbook? Only a key-rotation runbook is mentioned; there is no breach-detection or CNIL-notification procedure.
- Total cost of ownership and budget authority: electricity/thermal for the CPU box and future 3090 running 24/7, the interim worker-VM spend (potentially exceeding the rest of the stack), EU-hosted-Claude marche public costs. No facet owns the euro budget or who approves an overrun - the only number in the code is a ~5 USD operator cloud budget.
- RAG document ingestion governance: who curates official source documents, how updates and retractions propagate, how ACL provenance is assigned per document, and how retrieval behaves over satellite links. RAG is 'planned not built' but the human/editorial pipeline feeding it is unspecified.
- Language and accessibility: French-first is stated but there is nothing on Reo Maohi / Tahitian and other Polynesian languages, nor on RGAA accessibility compliance (mandatory for French public-sector digital services) for whatever client is built.

- Who is the named DPO / RGPD sign-off owner, and do they have real bandwidth for DPIA ownership plus a quarterly human review of legal-category answers? Round 1 flagged this role as unnamed; if it is fiction, the human-legal-review tiers and the api/legal/ artifacts are fiction.

- What latency/SLA commitment is politically acceptable to make to the directions metier - 'heures ouvrees, best effort' with no number, or a firm figure - and is an asynchronous 'answer delivered later by notification' model acceptable as the PRIMARY user experience rather than an exception?
- Sign-off on the frozen-cascade amendments already implied by Rounds 1-2: cascade capped at T4 by default, T5 becomes a deliberate escalation-only path, CLAUDE.md's 'figee' cascade table updated to match api/main.py reality (and the phantom Llama 3.3 corrected). - What retention period is accepted for the operational query store and the deferred queue (24-48h proposed), and is the loss of multi-day conversation memory that this implies acceptable as a product decision?
- Who owns, as funded named roles, the canonical answer base editorially (~0.3 FTE) and the prompt pack / GOVERNANCE.md? Without real staffing these decay into stale content that silently misleads agents.
- Are dolphin-mixtral and neural-chat (uncensored community fine-tunes) acceptable as the deployed code and legal tiers, or must the cascade move to the vetted models named in CLAUDE.md before go-live?
