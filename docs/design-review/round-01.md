## Highest-leverage change (this round)

The typed degradation response contract (part b of top_adopt rank 3): a service_level enum, requested-vs-served tier, and a closed-enum degradation_reason carrying zero query text, surfaced as a UI banner with a concrete next step and a single Prometheus served-below-requested gauge. It is size S, needs no GPU, touches only api/main.py response assembly plus the inline HTML, carries no RGPD or sovereignty risk of its own, and directly dissolves the stack's worst systemic pathology - 'fail-closed silently lowers answer quality with no user signal and no SLO'. Critically it is the precondition that makes every other change in this round measurable in production: without it, the eval harness measures a lab and nobody can see the real degradation rate. Derive the enum strictly from which error/fallback branch actually executed (Anone 503, OllamaError, T5 budget cap, moderation timeout), never from tier arithmetic, and keep the new SLO non-paging until a baseline exists.

## Top proposals to adopt (ranked, post-critique)

### 1. Routing + answer eval harness, landing first and gating every later change  
_facet: cascade-routing_

**Why:** Every cascade, anonymisation and model change proposed this round is currently unfalsifiable, and the brief's own 'model and prompt changes are unmeasured' is the root cause. A ~200-item labelled set with a gold category, a gold tier and an answer rubric turns each later change into a regression-gated diff. The routing-accuracy, cloud-call-rate and estimated-cost slices need no GPU, so they run in CI on the CPU-only box today, and they give Jazzy a defensible number for CNIL ('X% of traffic crossed the perimeter this month'). It must land first because proposals 4 and 6 both depend on the corpus. The one real cost the proposal understates: 200 real agent queries are personal data processed for a new purpose, so the corpus must be pseudonymised through Anone or synthetic, with a named owner, a documented purpose and a retention limit before it sits in the repo.

**Adoption sketch:** New api/eval/ directory; corpus as JSONL (query, gold_category, gold_tier, reference_answer, notes). A runner calls the router function directly for routing/cost/cloud-rate metrics and optionally hits a running stack for answer-quality. CI job runs routing + cost + cloud-rate only and reports deltas with human sign-off required on regressions (no hard absolute thresholds, so a genuinely better router is not ossified). Answer quality is a slower offline loop with a human or occasional-cloud judge. Label taxonomy owned in the same governance doc as the cascade. ~3-5 dev days plus ops annotation time.

### 2. Deterministic structured-PII layer before GLiNER plus a post-mask leak canary  
_facet: anonymisation-rgpd_

**Why:** GLiNER at threshold 0.5 is probabilistic and weakest on exactly the identifiers that are most damaging and most machine-checkable (NIR, IBAN) and on Polynesian toponyms its training barely saw. Regex plus checksum validators have near-zero false negatives on structured classes, cost microseconds, need no model, and the post-mask canary (re-run all detectors on the anonymised text, fail closed to local on any match) converts a silent recall miss into a local fallback instead of a cloud leak. This is the highest value-per-effort item in the round and the cheapest single reduction of the tail risk that makes the cloud path legally indefensible. The hidden work under the 'S' estimate is span merging: regex hits must be interval-merged with GLiNER spans with explicit overlap resolution, because the current right-to-left substitution assumes one non-overlapping source and will corrupt output otherwise.

**Adoption sketch:** Extend api/anone_api.py with a detectors module: NIR with cle de controle and 987/988 department codes, IBAN mod-97, +689 phone ranges, M365 email pattern, a DSI-supplied distinctive matricule format. Drop or gazetteer-back the loose PF address-marker regex (PK/servitude/district) because over-masking re-introduces the mask-the-subject quality loss. Run detectors unconditionally before GLiNER, merge spans with interval resolution, re-run after masking, fail closed on any residual match, emit a Prometheus counter and alert when the canary trips. Self-contained, no new service. ~2-3 days.

### 3. Fix the fallback path: escalate-or-degrade, typed degradation contract, dependency circuit breakers  
_facet: resilience-failure-modes_

**Why:** query_ollama_with_fallback today walks T4 to T3 to T2 to T1, handing the hardest question to the weakest model, and signals it only as a '[repli T4->T1]' string glued onto the answer. Three cheap fixes compose. (a) Treat OOM/timeout as an infrastructure event: retry in place, escalate one tier only if capacity is free, otherwise return degraded=true with no fabricated answer, never a silent downgrade. (b) A typed response contract (service_level enum nominal|degraded|deferred|unavailable, requested vs served tier, a closed-enum degradation_reason carrying zero query text, a UI banner with a concrete next step) so degradation stops being invisible and becomes an SLO, and every later prompt/model change becomes measurable against a degradation rate. (c) Per-dependency circuit breakers keyed strictly on connection-refused / 5xx / a cheap liveness probe, never on generation latency, since a healthy T4 answer already exceeds the current 120s httpx timeout, so one wedged Ollama model becomes a fast visible skip instead of a ~8-minute cascade of timeouts that piles up under concurrency. Also raise the real-call timeout to fit CPU inference.

**Adoption sketch:** All in api/main.py: ~40-line in-process breaker (per-model consecutive-failure count, open/half-open probe, liveness via Ollama /api/tags and Anone /health); rewrite the fallback loop to escalate or degrade; add response fields plus a closed reason enum derived from which error/fallback branch actually ran (not from tier distance, which the brittle router pollutes); small banner in the served HTML; new Prometheus served-below-requested gauge, observe-only until a baseline exists. Optional autoheal container behind a read-only docker-socket proxy with a restart-rate cap that pages instead of looping. ~4-6 days.

### 4. Decouple data residency from quality tier: remove T5 from auto-cascade, add an Article 9 on-prem gate  
_facet: sovereignty-boundary_

**Why:** Complexity score and 'may this leave the territory' are different questions and must not share a control. Cap the automatic cascade at T4 (fully local) and make crossing the boundary a separate deliberate per-query act: an Entra-role-restricted human sets 'cloud autorise' with a free-text justification that lands in an egress log, entering a distinct gated path that still enforces Anone plus the T5_MODERATION gate plus token/call caps (the flag chooses residency, it never bypasses anonymisation). Bundle the special-category hard gate: a cheap keyword/lexicon pass pins health, arret maladie, disciplinaire, sanctions, casier, appartenance syndicale to on-prem-only (T4 max, T5 structurally impossible regardless of human approval), with a GLiNER/small-model advisory second stage only when the lexicon fires. This kills the impossible-to-tune >=4.5 threshold, the 'scored 4.6 so it went to the US cloud' failure class, and the latent risk that a future keyword re-weighting silently opens the floodgates, and it makes the honest description 'local for ~100% of traffic, cloud only on explicit logged human request.'

**Adoption sketch:** api/main.py routing: cap auto-cascade at T4; add the explicit cloud path guarded by flag plus justification written to an egress log; add a lexicon gate module (curated French terms + regex) before routing with a user-visible 'donnees sensibles - traitement local uniquement' message; advisory model stage reuses the Anone model. UI affordance for the per-query flag (not per-session). ~3-4 days plus lexicon curation and an ops policy doc for who may set the flag. Amends the frozen cascade (T5 no longer auto-reachable) - needs Jazzy's sign-off.

### 5. Response cache 'T0' before the cascade, phased exact-match then semantic  
_facet: scaling-throughput_

**Why:** Government helpdesk traffic is dominated by a few hundred recurring questions (reset MDP, Outlook F3, VPN, conges). A cache hit costs ~100-300ms of CPU embedding versus 150+ seconds of generation, so a 40-70% hit rate is the single biggest concurrency lever available on one box, and the higher the hit rate the less the unsolved single-GPU capacity problem bites. It reuses multilingual-e5-base plus pgvector already on the RAG roadmap, so marginal infra cost is low. The hazards are real and must be designed for: semantic false positives ('poser des conges' vs 'annuler mes conges' embed nearly identically with opposite answers), the ACL-scoped key must default-deny and handle multi-group agents, PII must be screened on every cache write so Anone becomes a hard dependency of the write path (fail closed to no-cache when Anone is down), and entries go stale when procedures change.

**Adoption sketch:** New pre-cascade step in api/main.py. Phase 1: exact match on a normalised query hash (safe, still catches most repeat volume). Phase 2: semantic match behind a conservatively tuned cosine threshold plus a mandatory 'ce n'est pas ma question' feedback path and per-entry hit/quality telemetry. ACL-namespaced key, default-deny. TTL plus a manual purge endpoint from day one, wired to invalidate on future RAG /ingest and /doc DELETE so RGPD erasure is not defeated. Seed with a curated helpdesk FAQ and prefer it over generated answers until the feedback loop shows the semantic layer is safe. Add the cache log and stored embeddings to the DPIA with a retention limit. ~4-5 days for phase 1+2.

### 6. Replace the scalar complexity score with an embedding-kNN categorical intent classifier  
_facet: cascade-routing_

**Why:** A 1.0-5.0 scalar forces a false total order onto tiers that are actually domains: T3 Qwen (code) and T4 Mistral Small (legal) are not harder than each other, so no keyword weighting can place a query between them, and the bag-of-keywords is trivially gameable. A fixed category-to-tier map ({salutation, reformulation, code, analyse/synthese, juridique-RGPD-administratif} -> tier) is inspectable and gives the operator an auditable reason ('route T4 parce que classe juridique') instead of an opaque number. Implement as embedding-kNN over the proposal-1 corpus: one multilingual-e5-base forward pass (~100-300ms CPU), reusing the cache/RAG embedding path, never a per-query LLM classifier which would add a full generation to every 'bonjour' and roughly double trivial-query latency at ~3 tok/s. The classifier must never emit a 'besoin-cloud' label (cloud stays escalation-only behind proposal 4's human gate), and any un-maskable-nominative signal is advisory (warn / lower a tier), not a hard gate, given GLiNER recall.

**Adoption sketch:** Replace the scoring function in api/main.py and cascade_router.py with a kNN lookup against a stored label-embedding index in pgvector. The category-to-tier map is a small YAML in config/ owned in the same governance doc as the cascade. Fix the phantom TIERS list in the same change: main.py currently pins neural-chat / dolphin-mixtral / llama2:7b, not the CLAUDE.md models, and 'Llama 3.3 8B' does not exist as a released size. ~3-4 days after the corpus exists.

## Contradictions between proposals (and resolutions)

- Collapse local models (cascade-routing 'merge T1+T2', scaling-throughput 'collapse to 2 batching servers') vs the figee cascade and vs proposal 6's category-to-tier map. Resolution: do not unilaterally rewrite a cascade marked 'ne pas modifier'. Get the throughput benefit at config level first: pin two resident models in Ollama (keep_alive=-1, MAX_LOADED_MODELS) or one Ollama instance per model, and collapse only the routing decision. Present 'small / medium / cloud' plus the 22B-to-14B RGPD-quality tradeoff to Jazzy as an explicit signed decision. Keep Mistral Small 22B as a low-volume cold-swap tier for lexicon/human-flagged juridique queries, or validate 14B on the RGPD eval set before dropping it. Move to vLLM continuous batching only after the RTX 3090 driver is installed and verified.
- Local abstraction step for T5 (anonymisation-rgpd P1) vs remove T5 from auto-cascade (sovereignty P1) vs throughput reality. Resolution: adopt sovereignty P1 as the frame (T5 explicit-only, rare). On that rare path apply a reduced abstraction: rewrite the concrete case to a generic person-data-free question, but DROP the LLM re-application step (a weak local model stitching a legal ruling onto a named person produces fluent official-looking wrong answers). Return T5's generic answer plus unstitched local context labelled 'reponse generique - a valider par un agent'. Gate the whole feature on the eval harness. Two extra CPU passes are tolerable only because T5 is now rare.
- Durable query queue (resilience P2) and async job model (scaling P1) both persist raw pre-anonymisation query text in Postgres vs RGPD minimisation and vs the re-identification-key-as-regulated-artifact proposal (anonymisation P3). Resolution: these are the same queue, merge them. Run Anone at enqueue time and store ONLY anonymised text; if Anone is down you cannot enqueue and must tell the user. Hold pii_mapping encrypted or server-side in Anone. Hard 24-48h TTL enforced by the worker, documented in a DPIA. Mail carries a link only, answer retrieved in-app behind Entra auth. Token-bucket the queue drain on link recovery to protect the GPU and the T5 budget cap.
- Per-island edge appliance (resilience P3) vs central response cache (scaling P2) - overlapping, and the physical fleet is disproportionate for a small team. Resolution: adopt the central semantic cache now (proposal 5). Defer the physical appliance fleet until there is data on how many agents actually suffer multi-hour satellite outages and a committed A/B-partition appliance-management plan. Interim: a software-only PWA / service-worker offline mode caching each user's own recent non-PII Q&A in the existing workstation browser, no new hardware.
- Original cascade P1 'besoin-cloud' as a routable classifier label vs sovereignty P1 (cloud is never a destination the router picks). Resolution: sovereignty P1 wins. The classifier never emits a cloud label; the cloud tier is only ever reached by an explicit Entra-role-restricted human act behind the T5_MODERATION gate.
- Throughput-aware routing 'downgrade for load' (scaling P3) could in principle move a request toward T5. Resolution: hard rule - load-pressure downgrade may only move toward cheaper/local tiers, never toward cloud. Use queue wait / time-to-first-token as the pressure signal, not raw GPU utilisation, and implement it as a threshold rule on the merged queue, not a standalone control loop, and only after model-swap thrash is fixed.
- Opaque-id session store for pii_mapping (anonymisation P3) vs the reality that LangGraph already holds the full cleartext query. Resolution: adopt the register / no-persist half now (audit every logging and Postgres write path, guarantee pii_mapping and raw nominative queries are never persisted or logged, add a best-effort append-only pseudonymisation register off the hot path). Defer the opaque-id indirection until Anone is genuinely multi-worker or LangGraph is refactored into a lower-trust component.

## Threads to go deeper on (round 2)

- sovereignty-boundary: Is there ANY lawful basis for the T5 transfer? Concretely compare (a) Anthropic direct US API with DPA + SCCs + a post-Schrems II Transfer Impact Assessment against FISA 702, (b) Claude via an EU-hosted region (Bedrock/Vertex EU) to shrink the Chapter V problem, (c) zero-cloud with a local 32B or the T4 ceiling. Decide keep-cloud vs zero-cloud, and if the TIA cannot clear, what deletes T5 entirely.
- scaling-throughput: Build a concrete capacity model. Measure actual tok/s on the current CPU box, project realistic peak QPS from 5500 agents / 3500 workstations over an 8h window, state cache hit-rate assumptions, and derive what SLO is genuinely achievable CPU-only today vs after the single RTX 3090 - because a queue creates zero capacity and the published ETA may be hours until the cache and GPU land.
- anonymisation-rgpd: Design singling-out / quasi-identifier detection beyond GLiNER PII spans - rare PF toponyms, communes below a population threshold, precise date+role combinations - since GLiNER green-lights 'un agent de la mairie de Maupiti en arret psychiatrique depuis 6 mois'. Specify the gazetteer source, the heuristic, and exactly where mandatory human sign-off on the abstracted/anonymised text sits before any cloud call.
- resilience-failure-modes + scaling-throughput: Enumerate every store that holds nominative or reversibly-pseudonymised data - LiteLLM Postgres logs, LangGraph checkpointer state, the merged job queue, the response cache and its embeddings, the cloud egress ledger, the eval corpus - and produce ONE retention / erasure / access-control / DPIA design covering all of them, including how RAG DELETE /doc/{id} sweeps derived state.
- retrieval-rag: Sequencing. RAG's per-chunk ACL needs the orchestrator to have any authentication at all (port 8888 has none today), and Entra on-behalf-of is a stack-wide auth change. Define the minimum auth story for the orchestrator, whether RAG is even in scope this cycle, and who classifies each SharePoint/file-share source as cloud-eligible vs restricted at onboarding.
- cascade-routing: Validate the embedding-kNN classifier empirically - does it actually beat the keyword score on real (pseudonymised) DSI queries, what is the misclassification cost when it sends a query to the wrong specialist rather than one tier too low, and what is the exact category taxonomy and its governance owner?

## Facets / concerns the round missed

- Authentication and identity on the orchestrator itself: port 8888 has no auth today, yet every routing, ACL, cache-namespacing, approval-gate and egress-ledger proposal assumes a known caller identity. This is an unaddressed stack-wide prerequisite.
- The end-user client / UI: what 5500 agents actually interact with (web app? Teams bot? intranet portal?) and how approval gates, degradation banners, async/deferred answers, and the 'cloud autorise' flag surface there. Every proposal that adds a response field or a human decision assumes a UI that is never specified.
- Prompt and system-prompt management: the per-tier prompts are load-bearing (they define 'the legal model'), unversioned, and untested. No proposal covers where they live, how they are reviewed, or how a prompt change is gated by the eval harness.
- Model supply chain and updates: how models are pulled and integrity-verified (checksums/signatures), patched, and updated over satellite links; plus the CLAUDE.md errors (phantom 'Llama 3.3 8B', main.py TIERS pointing at neural-chat/dolphin-mixtral/llama2:7b) that mean the frozen cascade is not what is deployed.
- Business continuity: the single inference box is an unmitigated SPOF with no HA, no documented backup/restore for PostgreSQL (LiteLLM logs + LangGraph state + pgvector), and no disaster-recovery runbook.
- T5 cost governance beyond in-process caps: _t5_calls / _t5_seq are per-process in-memory and reset on restart; there is no persistent per-day or per-agent budget, no billing alert, no spend dashboard.
- Abuse / rate-limiting per agent and acceptable-use: 5500 users on a scarce resource with no per-user quota, and the tension between usage logging for capacity planning and the management-surveillance risk that logging agent questions creates.
- Secrets lifecycle beyond '.env, git-ignored': rotation of HF_TOKEN and the Anthropic API key, and what happens on compromise.
- Measurement of Anone itself: no GLiNER recall/precision baseline on Polynesian data, so the fail-closed canary's trip rate has nothing to be compared against.
- Polynesian languages: CLAUDE.md says French-first but reo Maohi / Tahitian and other territorial languages are never mentioned as input or output concerns for a government-wide tool.

- Is RAG in scope this cycle, and if so who is accountable for classifying each SharePoint site / file share as cloud-eligible ('general') vs restricted at onboarding?
- Retention periods: what does the DSI DPO mandate for LiteLLM logs, LangGraph state, the response cache, the job queue, the cloud egress ledger, and the pseudonymisation register?
- Are Polynesian languages (reo Maohi and others) in scope as input or output for the tool, or is it French-only?
